# rubric-evolve — 公式升级

## 这个 Skill 做什么

当你通过 post-retro 积累了足够的"预测 vs 实绩"配对数据后，把观察到的规律固化成 rubric 公式的升级——调权重、加减维度、重新定义 bucket 边界。

## 为什么需要它

v0 rubric 是等权占位——它不知道你的受众更在乎情感共鸣还是钩子强度。但 5 条复盘之后，数据会告诉你答案：比如"ER 高的帖子不管 HP 多低都有人藏"→ ER 权重应该上调。rubric-evolve 就是把这种发现变成公式更新的过程。

## 前置条件

| 条件 | 最低门槛 |
|---|---|
| 完整闭环数（predict → 发布 → retro） | ≥ 5 条 |
| 观察记录 | ≥ 3 条指向同一方向 |
| 或：用户主动发起 | 用户说"我觉得 XX 维度不准" |

不满足条件时 → 温和拒绝："你的校准数据还不够，建议再跑 N 条闭环再升级。现在强行改公式等于换一种方式猜。"

## 工作目录

从 `~/.social-media-sniffer/config.json` 读取 active workspace：`config.workspaces[config.active]`

rubric 文件：`<项目根>/rubrics/xhs-image-text-zero.md`（v0）→ 升级后写 `xhs-image-text-v1.md`

## 两种升级模式

### 模式 A：完整 rubric 升级（改权重/加减维度）

**触发**：用户说"升级 rubric"/"调整权重"/"我想加一个维度"

**流程**：

1. **读取所有复盘数据**：历史预测 + 实绩配对
2. **分析偏差模式**：
   - 哪些维度跟实绩正相关？（高分 → 实绩好）
   - 哪些维度是噪声？（分数高低跟实绩无关）
   - 有没有"隐藏维度"？（某种 pattern 总是 over-perform 但现有 7 维没覆盖）
3. **提出新公式**：
   ```
   旧：(ER + HP + QL + NA + AB + SR + SAT) / 7 × 2.0
   新：(ER×1.5 + HP×1.5 + QL + NA×0.5 + AB + SR + SAT) / 8.0 × 2.0
   理由：ER 和 HP 被数据证明是主驱动，NA 对图文影响很小
   ```
4. **回测验证**：用新公式重打所有历史样本的 composite，看新排序跟实绩排序是否更一致
   - 验证标准：≥ 4/5 样本的新排序与实绩排序一致 → 通过
   - 未通过 → 回退，告诉用户"新公式没比旧的好"
5. **用户确认**：展示新旧公式对比 + 回测结果，用户说 ok → 落盘
6. **落盘**：写新版本 rubric 文件（`xhs-image-text-v1.md`），旧版本保留

### 模式 B：Bucket 重校（只动桶边界，不动公式）

**触发**：用户说"我号长大了 bucket 不准了"/"重校桶"

**流程**：

1. 读最近 5-10 条的实绩数据
2. 算新的 baseline（中位数互动量）
3. 重新派生比率桶边界
4. 更新 rubric 文件的 bucket 段

比完整升级轻量得多，不需要回测。

## 升级纪律

### 按校准池规模限制动作幅度

| 校准池 | 允许的改动 |
|---|---|
| 5-9 条 | 修正维度定义（定性），如"把 HP=5 的标准写得更严"。第一次正式 bump 也在这档 |
| 10-19 条 | 微调权重 ±0.3（定量），如 ER ×1.0 → ×1.3 |
| 20+ 条 | 数据驱动——可用 correlation 分析反推权重 |

**关键**：不要在 N=5 时就用回归拟合——5 个点拟合 7 维公式必过拟合。

### 观察的生命周期

升级时必须清理观察记录：
- 被本次升级吸收为正式维度/权重的观察 → 标记"已吸收"
- 被新数据推翻的观察 → 标记"已推翻"
- 仍未解决的 → 保留，等更多数据

rubric 文件是"当前生效规则"，不是历史博物馆——读者打开它应该 60 秒内知道今天该怎么打分。

## 输出

新版本 rubric 文件，格式与 v0 相同但：
- 标题改为 `v1 已校准` / `v2 已校准`
- 公式段更新
- 权重理由段说明"为什么从等权改成这样"
- 底部附"升级 memo"：基于什么数据、什么观察、回测通过率

## 关键规则

1. **≥ 5 条闭环才能动公式**——这是最低门槛，不可商量
2. **回测必须通过**——新公式排序跟实绩排序一致性 ≥ 4/5 才落地
3. **旧版本保留**——不覆盖旧 rubric 文件，留作对照
4. **一次只做一种改动**——要么改权重，要么加维度，不要同时改多个东西（否则分不清哪个改动有效）
5. **用户确认才落地**——不自动升级

## 与其他 skill 的关系

- **上游**：post-retro 积累观察 → 触发 rubric-evolve
- **下游**：升级后的 rubric 被 draft-score、blind-predict 使用
- **回溯**：升级后不重写历史预测文件，但在预测 header 标注"基于 vN 公式"
- **联动**：creator-profile 数据面的发现可以作为升级的辅助证据（"受众其实不在乎 NA"）
